# Owl BLE 프로토콜 v1 (초안)

펌웨어(`firmware/`)와 앱(`android/`), PC 도구(`tools/`)가 공유하는 **계약서**예요.
이 문서를 바꾸면 세 곳을 같은 커밋에서 같이 고쳐야 해요.
레퍼런스 구현은 `tools/owlproto.py`이고, `tools/tests/`의 테스트가 이 문서의 숫자를 검증해요.

- 모든 정수는 **little-endian**
- `u8/u16/u32/u64` 부호 없음, `i16` 부호 있음
- 문자열 없음 (펌웨어 파싱을 단순하게 유지)

## 1. 설계 원칙

1. **기기는 녹음만, 판단은 폰이.** 기기는 오디오를 세그먼트 단위로 플래시에 쌓아두고, 폰이 연결되면 꺼내 가요.
2. **폰이 ACK하기 전엔 지우지 않는다.** 전송 중 끊겨도 데이터가 사라지지 않아요.
3. **기기 시계를 믿지 않는다.** 기기는 `(boot_count, uptime_ms)`만 기록하고, 실제 시각 변환은 폰이 해요(4장).
4. **풀(pull) 방식.** 기기가 먼저 데이터를 밀어내지 않아요. 폰이 목록을 묻고, 원하는 세그먼트를 요청해요. 재전송·이어받기가 쉬워져요.

## 2. GATT 서비스

Base UUID: `a269xxxx-8c8b-40f7-a91b-3ffa7ab560b9`

| 이름 | UUID (xxxx) | 속성 | 방향 | 용도 | 암호화 (2.4장) |
|---|---|---|---|---|---|
| Owl Service | `0001` | - | - | 서비스 | |
| STATUS | `0002` | Read, Notify | 기기 → 폰 | 배터리, 저장 공간, 미전송 개수 | 읽기는 없이도 됨, 구독(CCCD)은 필요 |
| CONTROL | `0003` | Write, Notify | 양방향 | 명령(폰→기기)과 응답(기기→폰) | 쓰기·구독 모두 필요 |
| DATA | `0004` | Notify | 기기 → 폰 | 세그먼트 바이트 스트림 | 구독 필요 |

광고 이름: `Owl-XXXX` (XXXX = 기기 주소 하위 2바이트 hex). 광고에 서비스 UUID 포함.

광고 간격: 평소 1초 (평균 약 0.01–0.02mA 추정, M5에서 측정). 기기는 켜져 있는 동안 늘 광고해서 폰이 언제든 연결할 수 있게 해요.

연결 파라미터 목표: MTU 247, 2M PHY, Data Length Extension(251), 연결 간격 15–30ms (전송 중) / 연결 해제 (평소).
Android 기준 실효 처리량은 대략 수십 KB/s로 잡아요 (측정 후 갱신).

### 2.1 STATUS (24바이트)

| 오프셋 | 타입 | 필드 | 설명 |
|---|---|---|---|
| 0 | u8 | proto_ver | `1` |
| 1 | u8×3 | fw_ver | major, minor, patch |
| 4 | u16 | battery_mv | 배터리 전압 (mV) |
| 6 | u8 | flags | bit0 충전 중(보류, 아래 참고), bit1 녹음 켜짐, bit2 저장 공간 부족(≥90%), bit3 저장 공간 가득 참, bit4 페어링 열림(2.4장) |
| 7 | u8 | reserved | `0` |
| 8 | u32 | storage_used_kb | |
| 12 | u32 | storage_total_kb | |
| 16 | u16 | pending_segments | 아직 ACK 안 된 세그먼트 수 |
| 18 | u16 | reserved | `0` |
| 20 | u32 | boot_count | 4장 참고 |

- bit1 녹음 켜짐: 사용자가 녹음을 끄지 않은 상태(버튼 2초 또는 SET_RECORDING). 저장 공간이 가득 차서 멈춘 경우에도 1이고, 그건 bit3으로 알아요.
- bit0 충전 중: 보드에 충전 상태를 읽을 핀이 없어서(회로도 V1.2) 지금은 항상 `0`. 쓸지는 [PRD 10장](../docs/prd.md#10-미결정-사항) H.
- 기기가 꺼져 있으면(버튼 5초, 배터리 부족) 광고도 꺼져서 STATUS를 읽을 수 없어요. 폰은 "연결 끊김"으로만 알아요.

배터리 잔량(%)은 폰이 전압 곡선으로 계산해요. 기기에 곡선을 넣으면 배터리를 바꿀 때마다 펌웨어를 고쳐야 해서요.

### 2.2 CONTROL

요청(폰 → 기기, Write With Response):

```
[op u8][seq u8][payload ...]
```

응답(기기 → 폰, Notify):

```
[op | 0x80][seq u8][result u8][payload ...]
```

`seq`는 폰이 매기는 0–255 순환 번호. 응답은 같은 `seq`를 돌려줘요.

TIME_SYNC의 `tz_offset_min`은 기기가 쓰지 않아요(시각 변환은 폰이 해요, 4장). 자리만 잡아둔 필드예요.

| op | 이름 | 요청 payload | 응답 payload |
|---|---|---|---|
| `0x01` | TIME_SYNC | `unix_ms u64`, `tz_offset_min i16` | `boot_count u32`, `uptime_ms u64` |
| `0x02` | LIST_SEGMENTS | `after_id u32`, `max u8` | `count u8`, 그 뒤 `count`개의 `{id u32, type u8, size u32}` (9바이트씩) |
| `0x03` | FETCH_SEGMENT | `id u32`, `offset u32` | 없음 (데이터는 DATA로 옴) |
| `0x04` | ACK_SEGMENT | `id u32`, `crc32 u32` | 없음. CRC가 맞으면 기기는 해당 세그먼트를 지울 수 있음 |
| `0x05` | ABORT | 없음 | 없음. 진행 중인 FETCH 중단 |
| `0x06` | SET_RECORDING | `on u8` (0 끄기, 1 켜기) | 없음. 녹음 켜짐 상태를 바꾸고 이벤트 2/3(arg 1 앱)을 남김 |
| `0x07` | UNPAIR | 없음 | 없음. 응답을 보낸 뒤 기기가 **모든 본딩을 지우고** 연결을 끊음(2.4장) |
| `0x10` | SET_CONFIG | `key u8`, `value u32` | 없음 |

`result`: `0` OK, `1` 알 수 없는 op, `2` 잘못된 길이, `3` 세그먼트 없음, `4` CRC 불일치, `5` 바쁨.

LIST_SEGMENTS 응답 하나에 들어가는 최대 개수: (244 − 4) / 9 = **26개**. 더 있으면 마지막 id로 다시 요청해요.

SET_CONFIG 키 (초안):

| key | 의미 | 기본값 |
|---|---|---|
| `1` | Opus 비트레이트 (bps) | 16000 |
| `2` | VAD 민감도 (0–3) | 2 |
| `3` | 세그먼트 최대 길이 (초) | 300 |

### 2.3 DATA

```
[segment_id u32][offset u32][bytes ...]
```

헤더 8바이트. MTU 247이면 ATT payload 244바이트 → 청크당 **236바이트**.
`offset`은 세그먼트 처음부터의 바이트 위치. 폰은 offset이 비면(패킷 유실, 재연결) 그 위치부터 FETCH_SEGMENT를 다시 보내면 돼요.
세그먼트 전체를 받으면 폰이 CRC32를 계산해서 ACK_SEGMENT로 보내요.

### 2.4 보안 (본딩)

보안이 없으면 근처의 누구나 녹음을 내려받고 ACK로 지울 수 있어요(PRD N8). 그래서 기기는 **본딩된 폰과의 암호화된 연결**에서만
명령을 받아요(`decisions.md` #33–#38).

용어: **페어링**은 두 기기가 암호화 키를 정하는 과정, **본딩**은 그 키를 양쪽에 저장해 두는 것이에요. 본딩해 두면 다음 연결부터는
묻지 않고 저장된 키로 바로 암호화해요.

**방식**

- LE Secure Connections 페어링만 받아요(옛 방식 LE legacy pairing은 거절).
- 기기에 화면·키패드가 없어서 **Just Works**(IO capability NoInputNoOutput)예요. 폰은 확인 창만 띄우고 숫자는 없어요.
  페어링하는 순간의 중간자 공격은 못 막지만, 그 순간이 아래 "페어링 창" 안으로 좁아요.
- 본딩하지 않는 페어링 요청(Pairing Request의 Bonding 플래그 0)은 거절해요.
- 암호화 수준은 Security Mode 1 Level 2(암호화, 인증 없음)면 돼요.

**속성별 권한**

| 대상 | 암호화 없는 연결에서 |
|---|---|
| STATUS 값 읽기 | 됨 |
| STATUS·CONTROL·DATA의 CCCD 쓰기(구독) | 안 됨 |
| CONTROL 쓰기 | 안 됨 |

STATUS를 열어 둔 이유: 녹음 내용이 없고(배터리·저장 공간·미전송 개수·부팅 번호) 아무것도 바꾸지 못해요. 대신 등록 전인 폰이나 PC가
"지금 페어링이 되는지"(bit4)를 먼저 알 수 있어서 거절될 때 알맞은 안내를 할 수 있어요. 대가로 근처의 사람이 미전송 개수 같은
활동량 힌트를 볼 수 있어요(`decisions.md` #36).

**연결 흐름**

1. 본딩된 폰이 연결하면 기기가 바로 Security Request를 보내고, 폰은 저장된 키로 암호화해요. Android 12–15는 이 요청이나
   ATT 오류가 있어야 암호화를 시작해서 기기가 먼저 요청해요. 모르는 상대에게는 보내지 않아요(아무 폰에나 페어링 창이 뜨지 않게).
2. 암호화 전에 막힌 속성을 건드리면 ATT 오류가 와요.
   - `0x05` Insufficient Authentication: 이 상대와 본딩이 없음
   - `0x0F` Insufficient Encryption: 본딩은 있는데 아직 암호화 전
3. Android·BlueZ는 이 오류를 받으면 스스로 페어링(또는 암호화)을 하고 다시 시도해요. 기기가 페어링을 거절하면 SMP Pairing Failed
   (`0x08` Unspecified Reason)를 보내고, Android 앱은 GATT status `137`(GATT_AUTH_FAIL)을 받아요.
4. 연결 뒤 **60초**(`UNENCRYPTED_TIMEOUT_MS = 60000`) 안에 암호화되지 않으면 기기가 연결을 끊어요(HCI reason `0x05`
   Authentication Failure). 기기는 한 번에 하나만 연결되니, 모르는 상대가 그 자리를 붙잡고 있지 못하게 하려는 거예요.
5. 폰은 본딩이 있는데 기기가 그 본딩을 지운 경우(다른 폰이 등록함, UNPAIR): 기기가 저장된 키를 거절해요(HCI `0x06`
   PIN or Key Missing). 폰은 다시 등록해야 해요. Android 앱이 받는 신호는 버전마다 달라요(12–15는 GATT status `137`,
   16+는 폰이 스스로 끊고 암호화 실패 브로드캐스트. `android/README.md` 본딩, `decisions.md` #43).

**페어링 창** — 새 페어링을 받는 때

| 기기 상태 | 새 페어링 |
|---|---|
| 본딩된 폰이 없음(새 기기, UNPAIR 뒤) | 언제나 받음 |
| 본딩된 폰이 있음 | 기기를 켠 뒤 **120초**(`PAIRING_WINDOW_MS = 120000`) 안에서, 그 창에서 아직 새 본딩이 생기지 않았을 때만 |

- "켠 뒤"는 전원이 켜져 BLE가 시작된 때부터예요(버튼 5초로 켜기, 충전 후 자동 켜기, 그 밖의 재시작 모두). 꺼진 채 전압만 확인하고
  다시 잠드는 경우는 BLE를 켜지 않아서 창도 없어요.
- 창 안에서 새 본딩이 하나 생기면 그 부팅의 창은 닫혀요. 그래서 등록한 직후 옆 사람이 다시 페어링해 바꿔치기할 수 없어요.
- 거절은 SMP 단계에서 해요(위 흐름 3). 이미 본딩된 폰이 다시 암호화하는 것은 페어링이 아니라 창과 상관없어요.
- STATUS bit4 = 지금 새 페어링을 받는지. 창은 시간이 지나 닫히므로 알림 없이 바뀔 수 있어요. 필요하면 다시 읽어요.

**본딩은 하나**

- 기기는 폰 하나와만 본딩을 유지해요. 새 본딩이 완료되면 그 밖의 본딩을 모두 지워요. 새 페어링이 실패하면 이전 본딩은 그대로예요.
- 같은 폰이 다시 페어링해도 돼요(폰이 본딩을 지운 경우). 창 안이어야 하는 건 같아요. 키는 새 것으로 바뀌어요.

**등록 해제와 폰 바꾸기**

| 상황 | 방법 |
|---|---|
| 앱에서 "등록 해제" | 앱이 UNPAIR(`0x07`)를 보내요 → 기기가 응답 뒤 모든 본딩을 지우고 끊음 → 앱이 폰 쪽 본딩과 CDM 등록을 지움. 이후 기기는 아무 폰과도 페어링돼요(본딩 없음) |
| 폰을 잃어버림·초기화 | 기기를 껐다 켜고(버튼 5초 두 번) 2분 안에 새 폰으로 등록 → 옛 폰의 본딩은 새 본딩이 생길 때 지워짐 |
| 기기가 꺼져 있을 때 등록 해제 | UNPAIR를 못 보내도 폰 쪽은 지워요. 나중에 다시 등록하려면 위의 "껐다 켜고 2분 안에" |

버튼으로 본딩을 지우는 동작은 없어요. 껐다 켜기로 창을 여는 것으로 충분하고, 버튼 동작(짧게·2초·5초)을 늘리지 않으려는 거예요
(`decisions.md` #37).

**호환**

와이어 포맷은 그대로라 `proto_ver`는 `1`이에요(7장). 늘어난 것은 STATUS bit4(예전엔 늘 0)와 op `0x07`(예전 기기는 result 1
"모르는 op")뿐이에요. 예전 클라이언트도 Android·BlueZ가 ATT 오류를 받으면 스스로 페어링하므로, 창 안이거나 본딩이 없으면 그대로 동작해요.

## 3. 세그먼트 포맷

기기 플래시와 BLE 전송에서 **같은 바이트 그대로** 써요. 변환 코드가 없으면 버그도 없어요.
플래시에서는 세그먼트 하나가 LittleFS 파일 하나예요. ACK를 받으면 그 파일을 지워요(`decisions.md` #18).

예외 하나: 플래시에서는 헤더의 `payload_len`을 `0xFFFFFFFF`로 두고, 기기가 보낼 때 `size − 32`로 채워요. 파일 앞부분을 고치면 LittleFS가 뒤 블록을 전부 다시 써서, 세그먼트를 닫을 때마다 두 번 쓰게 되기 때문이에요. BLE로 나가는 바이트는 위 포맷 그대로예요(`decisions.md` #27).

### 3.1 헤더 (32바이트)

| 오프셋 | 타입 | 필드 | 설명 |
|---|---|---|---|
| 0 | u8×4 | magic | `"OWLS"` |
| 4 | u8 | version | `1` |
| 5 | u8 | type | `1` 오디오, `2` 이벤트 로그 |
| 6 | u8 | codec | `0` PCM16, `1` Opus (type=2면 `0`) |
| 7 | u8 | frame_ms | Opus 프레임 길이 (보통 20) |
| 8 | u32 | id | 세그먼트 번호 (단조 증가, 재부팅해도 이어짐) |
| 12 | u32 | boot_count | 녹음 시작 시점의 부팅 번호 |
| 16 | u64 | start_uptime_ms | 해당 부팅 기준 시작 시각 |
| 24 | u16 | sample_rate_div100 | 16000Hz → `160` |
| 26 | u8 | channels | `1` |
| 27 | u8 | reserved | `0` |
| 28 | u32 | payload_len | 헤더 뒤 바이트 수 |

### 3.2 오디오 payload (type=1)

```
반복: [len u16][Opus 패킷 len 바이트]
```

프레임 수 × frame_ms = 녹음 길이. VAD로 끊긴 구간은 세그먼트를 새로 시작해요(무음은 저장하지 않음).

### 3.3 이벤트 payload (type=2)

```
반복: [uptime_ms u64][event u8][arg u8]
```

| event | 의미 | arg |
|---|---|---|
| `1` | 북마크 (버튼 짧게) | 0 |
| `2` | 녹음 꺼짐 | 원인: `0` 버튼(2초), `1` 앱 |
| `3` | 녹음 켜짐 | 원인: `0` 버튼(2초), `1` 앱 |
| `4` | 저장 공간 가득 참 (녹음 멈춤) | 0 |
| `5` | 배터리 부족 (3.6V 아래) | 0 |
| `6` | 기기 꺼짐 | 원인: `0` 버튼(5초), `2` 배터리(3.5V 아래) |
| `7` | 기기 켜짐 | 원인: `0` 버튼(5초), `3` 충전 확인 후 자동, `4` 그 밖의 재시작 |

이벤트는 생길 때마다 바로 플래시에 써요(`decisions.md` #19). 상태를 바꾸는 이벤트(2, 3, 6, 7)는 바뀐 **결과**를 적어서, 중간 이벤트가 빠져도 폰이 상태를 잘못 이어 붙이지 않아요.

## 4. 시간 처리

기기에는 RTC 배터리가 없고, 재부팅하면 uptime이 0부터 다시 시작해요. 그래서:

1. 기기는 부팅할 때마다 `boot_count`를 1 올려 플래시에 저장해요.
2. 모든 기록은 `(boot_count, uptime_ms)`로만 남겨요.
3. 폰은 연결할 때마다 TIME_SYNC를 보내고, 응답으로 받은 `(boot_count, uptime_ms)`와 자기 시각을 짝지어 저장해요.
4. 세그먼트의 실제 시각 = 같은 `boot_count`의 sync 기록에서 역산.

같은 부팅 안에서 한 번이라도 sync가 있으면 그 부팅의 모든 기록 시각을 복원할 수 있어요.
sync 없이 재부팅된 부팅 구간은 시각을 "알 수 없음"으로 표시해요(앞뒤 sync로 대략 추정은 가능).

## 5. 동기화 흐름

폰이 시작해요. 기기가 근처에 있는 동안 **15분마다** 아래 흐름을 돌리고, 앱의 "지금 동기화"와 앱을 켤 때도 바로 시작해요.
연결이나 요청이 실패하면 앱이 정한 횟수만큼 다시 시도하고, 그래도 실패하면 앱은 기기를 "연결 끊김"으로 표시해요(`decisions.md` #15, #16).

```
폰                                   기기
 │── connect, MTU 247, 2M PHY ───────▶│
 │◀──────────── Security Request ─────│  (본딩된 폰만, 2.4장)
 │── 저장된 키로 암호화 ─────────────▶│
 │── subscribe STATUS/CONTROL/DATA ──▶│
 │── TIME_SYNC ──────────────────────▶│
 │◀───────────── boot_count, uptime ──│
 │── LIST_SEGMENTS(after=0) ─────────▶│
 │◀──────────── [{id,type,size}, ...] │
 │── FETCH_SEGMENT(id, 0) ───────────▶│
 │◀──────── DATA chunk × N ───────────│
 │   (CRC32 계산, 로컬 저장)          │
 │── ACK_SEGMENT(id, crc) ───────────▶│  → 기기: 삭제 가능 표시
 │   ... 다음 세그먼트 반복 ...       │
 │── disconnect ─────────────────────▶│
```

폰은 받은 세그먼트를 **디스크에 먼저 저장한 뒤** ACK해요. 순서가 바뀌면 앱이 죽었을 때 데이터가 사라져요.

### 5.1 세부 규칙

위 표와 흐름만으로 정해지지 않던 부분이에요. 펌웨어·앱·`tools/`가 모두 이 규칙대로 구현돼 있어요(`decisions.md` #28).

| # | 상황 | 규칙 |
|---|---|---|
| 1 | LIST 끝 판정 | 기기는 MTU에 맞게 한 응답의 개수를 26개보다 줄일 수 있어요. 개수가 적다고 끝이 아니에요. 폰은 `after_id` = 마지막 id로 계속 물어보고, **빈 응답(count 0)** 을 받으면 끝이에요 |
| 2 | LIST `size` | 헤더 32바이트를 포함한 세그먼트 전체 바이트 수 |
| 3 | FETCH 도중 FETCH | 새 FETCH가 진행 중인 전송을 대체해요. 폰은 빈 곳부터 다시 받을 때 ABORT를 먼저 보내요 |
| 4 | FETCH `offset == size` | result 0, DATA 없음 |
| 5 | 전송 끝 | DATA에 끝 표시는 없어요. 폰은 `[0, size)`가 다 채워지면 끝으로 봐요. 2초 동안 DATA가 없으면 멈춘 걸로 보고 ABORT 후 첫 빈 offset부터 다시 FETCH |
| 6 | DATA 청크 크기 | MTU − 3 − 8 (MTU 247이면 236). 폰은 offset으로만 조립해요 |
| 7 | 이벤트 세그먼트 | 기기는 폰이 연결할 때(그리고 LIST 때) 열려 있던 이벤트 로그를 닫아 LIST에 나오는 세그먼트로 만들어요. 그 뒤 이벤트는 새 세그먼트에 써요. LIST에 나온 세그먼트는 크기가 바뀌지 않아요. 부팅이 바뀌면 이벤트 세그먼트도 새로 시작해서, 세그먼트 안의 모든 이벤트는 헤더의 `boot_count`에 속해요 |
| 8 | PCM16 (codec `0`) | Opus와 같은 `[len u16][bytes]` 틀 |
| 9 | 잘못된 값 | SET_CONFIG의 모르는 key·범위 밖 값, FETCH `offset > size` → result `2` |
| 10 | 1바이트 요청 | seq가 없으므로 seq `0`, result `2`로 응답 |
| 11 | SET_RECORDING 같은 상태로 | result `0`, 이벤트 남기지 않음(상태가 실제로 바뀔 때만 이벤트) |

## 6. 저장 용량과 동기화 주기

| 항목 | 값 |
|---|---|
| Opus 16kHz 모노 16kbps | 2 KB/s = 약 7.2 MB/h |
| 플래시 16MB 중 오디오 영역 (약 15MB 가정) | **약 2시간 분량의 음성** |
| 12kbps로 낮추면 | 약 2.8시간 |

VAD로 무음을 빼도 대화가 많은 날은 하루 음성이 이보다 길어요. 그래서 **폰이 근처에 있으면 15분마다 동기화**해요(5장).
폰 없이 2시간 넘게 말하면 플래시가 차요. 그러면 새 녹음을 멈추고(STATUS bit3, 이벤트 4) 폰이 가져가 공간이 생기면 다시 녹음해요. 오래된 것을 덮어쓰지 않아요(`decisions.md` #17).

## 7. 버전 관리

- 호환이 깨지는 변경 → STATUS `proto_ver`와 세그먼트 `version`을 올려요.
- 필드 추가는 reserved를 먼저 쓰고, 부족하면 끝에 붙여요(길이로 구분).
