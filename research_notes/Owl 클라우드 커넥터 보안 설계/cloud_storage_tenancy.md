# Owl cloud: securing multi-tenant lifelog storage (at rest, from the operator, with third-party access)

Scope: the cloud storage side of an "Owl cloud" (sync of transcripts, optional audio, GPS history, bookmarks; served to MCP clients and OAuth third-party apps). MCP auth, prompt injection and the offline/personal case are covered elsewhere and are not repeated here.

Source labels: **[P]** = primary (vendor, regulator, researcher's own disclosure, statute/official stats). **[S]** = secondary (news, blogs, aggregators, competitor marketing). **[T]** = a well-known primary URL cited from prior knowledge. I did not re-fetch it in this session, so check it before quoting. Research date: 2026-11-08.

## 1. Encryption models and the E2EE vs. third-party-access tension

### Takeaway
Server-side envelope encryption with per-user data keys is the baseline. It protects against stolen disks and backups, and crypto-shredding gives real deletion, but the operator can still decrypt. True E2EE (Apple ADP, Android backups, Signal) removes operator access, but it is incompatible with a server answering third-party or MCP queries over plaintext. The products that still promise "even we can't read it" while running server-side AI on the data (Bee Private Compute, Apple PCC, Limitless "Confidential Cloud") all use attested confidential computing as the hybrid. Of those, only Apple's has substantial public verification tooling.

### Cited Findings
**Server-side, per-tenant envelope encryption / crypto-shredding**
- Envelope encryption: a KMS key wraps per-object or per-tenant data keys, and the data keys encrypt records locally. A KMS Encrypt call is limited to 4,096 bytes, which is why data keys are used for bulk data — [S: oneuptime guide](https://oneuptime.com/blog/post/2026-02-12-kms-envelope-encryption/view); [P: AWS KMS cryptography essentials](https://docs.aws.eu/kms/latest/developerguide/kms-cryptography.html)
- AWS reference designs exist for per-tenant keys. One uses one KMS key per tenant held in a central account, built to keep cost down [P: AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/simplify-multi-tenant-encryption-with-a-cost-conscious-aws-kms-key-strategy). Another caches data keys partitioned by tenant KMS key ARN, so each tenant's key material stays cryptographically isolated [P: AWS Security Blog](https://aws.amazon.com/blogs/security/caching-kms-data-keys-in-multi-thread-environments-per-tenant-encryption-for-event-driven-systems-at-scale/)
- Crypto-shredding works only at the scope where a key is unique. A shared key can't be destroyed for one user without affecting the others. It also erases "every copy" only if backups are encrypted under that same key — [S: WorkOS, cryptographic key isolation](https://workos.com/blog/cryptographic-key-isolation-multi-tenant-saas); [S: AWS Builder Center, cryptographic erasure with KMS](https://builder.aws.com/content/3BOLPCayV1YAQD0ScQZ2Rc1YoeZ/cryptographic-erasure-a-data-deletion-strategy-using-aws-kms)
- Counterpoint: per-tenant keys may not pay off when the backup system has no per-tenant backups to destroy — [S: handbook guide](https://handbook-docs-d0v.pages.dev/docs/architecture/security/data-protection/envelope-encryption)
- AWS KMS charges per customer-managed key per month, plus extra for rotation, so designs with one KMS key per user get expensive at scale. The usual pattern is one KMS key wrapping per-user data keys stored in the database — [S: summary of AWS pricing in search results](https://aws.amazon.com/blogs/architecture/simplify-multi-tenant-encryption-with-a-cost-conscious-aws-kms-key-strategy)
- KMS key deletion is scheduled with a mandatory 7–30 day waiting period (default 30). That defines the real crypto-shred latency — [T: AWS KMS "Deleting AWS KMS keys"](https://docs.aws.amazon.com/kms/latest/developerguide/deleting-keys.html)

**Client-side / E2EE precedents**
- Apple iCloud: some categories (e.g. Health, iCloud Keychain passwords) are E2EE by default, and Apple holds no keys for them. Advanced Data Protection (ADP) extends E2EE to more categories, including iCloud Backup and Photos. Current counts are 15 by default and 25 with ADP; older 2022 docs said 14 and 23. Calendar, Contacts and Mail stay non-E2EE because they must interoperate with servers and protocols. ADP requires a recovery contact or recovery key — [P: Apple, iCloud data security overview](https://support.apple.com/102651); [P: Apple Platform Security, ADP](https://support.apple.com/guide/security/sec973254c5f/web); [S: MacRumors 2022](https://www.macrumors.com/2022/12/07/apple-advanced-data-protection)
  - Relevance to Owl: Apple leaves data that third-party protocols need to read (CalDAV/CardDAV/IMAP) outside E2EE. That is the same trade-off Owl faces with an OAuth/MCP API.
- Android backup E2EE (Android 9+): the backup key is wrapped with the user's lock-screen PIN or pattern and then encrypted to a Titan HSM in Google's datacenter. The HSM enforces a guess limit, and its firmware can't be updated without wiping the chip. "No one (including Google) can access a user's backed-up application data without specifically knowing their passcode." NCC Group audited it — [P: Google Security Blog, Oct 2018](https://security.googleblog.com/2018/10/google-and-android-have-your-back-by.html); [S: Sophos](https://news.sophos.com/en-us/2018/10/16/google-using-lock-screen-passwords-to-encrypt-android-cloud-backups/)
  - Relevance: this is a model for recovering user-held keys (a low-entropy PIN plus a server-side HSM with a guess limit) without the operator being able to decrypt.
- Signal Secure Value Recovery uses SGX enclaves, later moving to multi-enclave consensus, for PIN-based key recovery — [T: Signal blog "Technology Preview: Secure Value Recovery"](https://signal.org/blog/secure-value-recovery/). I did not re-verify this in this session.

**Hybrids that keep server-side processing of plaintext**
- Apple Private Cloud Compute (PCC) has five stated requirements: stateless computation, enforceable guarantees, no privileged runtime access, non-targetability, and verifiable transparency. Every production image is published, devices check server attestations against a public transparency log, and Apple ships a Virtual Research Environment (VRE), source for some components, and a bug bounty. Apple has since extended PCC to Google Cloud while keeping "the same transparency guarantees" and its own control of software and attestation — [P: Apple Security Research, "Expanding Private Cloud Compute"](https://security.apple.com/blog/expanding-pcc); [S: SecurityWeek](https://www.securityweek.com/apple-opens-private-cloud-compute-for-public-security-inspection/); [S: Converge Digest](https://convergedigest.com/apple-extends-private-cloud-compute-beyond-apple-data-centers/)
  - Caveat: PCC is stateless. It processes a request and deletes the data, and it is not a data store. It does not solve "store a year of transcripts and let a third party query them."
- Amazon Bee "Bee Private Compute" (Sept 23, 2026): transcripts and insights are encrypted with keys "only your device creates and controls" ("Amazon has no master key"). Audio is "processed entirely in memory and immediately deleted." Processing runs on the AWS Nitro System and NitroTPM in an environment "no one, including Amazon and Bee, can access." The device checks that the server runs "approved, trusted software" (attestation) before sending data, Sigstore public ledgers are used for verification, and Trail of Bits did a review (PDF dated 2026-09). The page gives no retention period for transcripts — [P: Bee blog](https://bee.computer/blog/private-ai). I did not read the white paper or the Trail of Bits PDF.
  - Independent commentary: these are first-party claims, not an independent privacy audit. Sources conflict on AI-training use — [S: Pebblous](https://blog.pebblous.ai/blog/amazon-bee-audio-deleted-transcript-kept/en/); [S: Cybernews](https://cybernews.com/tech/amazons-bee-wearables-privacy-concerns/); [S: 9to5Amazon](https://9to5amazon.com/amazon-bee-privacy-explained/)
- Limitless "Confidential Cloud" claimed HSM-backed encryption and user-controlled keys, so employees couldn't access raw audio. No independent audit was found. After Meta acquired it (Dec 5, 2025), Rewind capture was disabled on Dec 19, 2025, service ended in the EU and UK, and continuing users had to accept Meta's terms. Data not exported by Dec 19, 2025 was to be permanently deleted. Critics noted that the ~14-day export window was short, and that "your data will remain safe" is a policy promise, not a cryptographic one — [S: 9to5Mac](https://9to5mac.com/2025/12/05/rewind-limitless-meta-acquisition/); [S: TechInformed](https://techinformed.com/meta-acquires-limitless-pendant-users-moved-to-free-unlimited-plan/); [S: Neowin](https://www.neowin.net/amp/meta-acquires-ai-startup-limitless-ending-sales-of-its-popular-pendant-wearable/); [S: Pascal's Chatbot analysis](https://p4sc4l.beehiiv.com/p/limitless-ai-a-case-study-in-how-small-hardware-enabled-ai-companies-transition-their-products-user)
- Plaud: AES-256 at rest and TLS 1.3 in transit (one review says TLS 1.2+), hosted on AWS with regional storage. Audio and transcripts are not kept in the cloud unless Cloud Sync is on. With sync off, the cloud is used only on demand for AI processing, with no persistent copy. No training on user data unless the user opts in — [P: Plaud Trust Center](https://www.plaud.ai/pages/trust); [P: Plaud support, security and compliance](https://support.plaud.ai/hc/en-us/articles/57744166222489-Plaud-s-security-and-compliance); [S: Layer3Labs](https://www.layer3labs.io/guides/is-plaud-hipaa-compliant)
- General TEE building blocks: AWS Nitro Enclaves (attestation documents tied to KMS key policies, so a key releases only to an enclave with a specific measurement), Google Confidential Space and Confidential VMs, and Azure confidential computing — [T: AWS Nitro Enclaves cryptographic attestation](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html); [T: Google Confidential Space](https://cloud.google.com/docs/security/confidential-space). I did not re-verify these in this session.

### Inferences
- Design options for Owl, roughly from least to most operator-resistant:
  1. **Server-side encryption (SSE) + per-user data key (DEK) + KMS.** Third-party, MCP and search features are simple. It protects against storage theft, stray backups and partial insider access (database admins without KMS rights). Crypto-shredding handles deletion. The operator, and anyone who compels the operator, can still read everything.
  2. **SSE + per-grant decryption scopes.** Each user's DEK is split per data type (transcripts / location / bookmarks / audio), so a third-party grant (OAuth scope) can unwrap only the keys for its types. KMS encryption context (user_id, data_type) ties every decrypt to an audit log entry the user can see. This adds no cryptographic protection against the operator, but every access is logged and scoped.
  3. **Phone-as-relay.** The cloud stores ciphertext only, with keys on the phone, as Owl does today. Third-party and MCP requests are queued and the phone answers them, decrypting locally and returning only the requested slice. The operator can't read anything. The costs: answers depend on the phone being online (latency, battery, Android background limits), and the third party still gets plaintext for whatever it is granted.
  4. **Attested TEE (Bee/PCC model).** Ciphertext is stored, and keys are released (via KMS attestation policy or keys sent from the device) only to an enclave running published code that applies the grant policy and returns results. This is the only option that offers "the operator can't read it" together with always-on third-party access. It needs reproducible builds, a transparency log and outside audits to be credible, which is heavy for a small team. Bee needed Amazon-scale resources plus Trail of Bits to make the claim.
- Whatever option is chosen, once a third party or MCP client receives plaintext, Owl's protection ends. Encryption protects the store, not the data after a grant.
- Option 3 matches Owl's current offline-first stance and its PRD line that data lives only on the phone. Options 1 and 2 are a much larger change to that promise. Any of them needs a `docs/prd.md` and `docs/decisions.md` update (per CLAUDE.md).
- Acquisitions break policy-based promises (Limitless→Meta). Only cryptographic or architectural guarantees, such as user-held keys or data that never leaves the device, survive a change of owner.

### Gaps
- I did not read the Bee white paper or the Trail of Bits report, so whether Bee uses Nitro Enclaves or other Nitro TEE features, and how keys are released, is unverified.
- I did not fetch Proton's architecture (zero-access encryption for Drive and Mail) or the current Signal SVR3 documents.
- I found no public example of a consumer lifelog product doing per-grant cryptographic key release to third-party OAuth apps. This looks novel and unproven.

## 2. Tenant isolation, BOLA/IDOR, and real incidents

### Takeaway
Broken object-level authorization (BOLA) is the #1 OWASP API risk. Every consumer-AI and wearable incident found here comes down to missing authorization or exposed secrets, not to broken encryption: Tea (open Firebase bucket plus an API that let one user's key reach other users' DMs), Rabbit r1 (hardcoded provider keys), and Omi (auth bypasses, a committed encryption secret, unauthenticated shared conversations). Defense in depth means object-level checks in code, database-enforced row-level security (RLS) keyed to the authenticated principal, and per-user keys, so that one missed check doesn't leak all users.

### Cited Findings
**OWASP / patterns**
- API1:2023 BOLA: attackers change an object ID in a request. "Every API endpoint that receives an ID of an object, and performs any action on the object, should implement object-level authorization checks." Comparing the JWT user ID with the ID parameter covers only a small subset of cases. Recommended: random or unguessable IDs (GUIDs) and tests for the authorization mechanism. BFLA, a caller reaching a function it shouldn't, is a separate category — [P: OWASP API Security Top 10 2023, API1](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)
- Postgres RLS: with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus policies (e.g. `USING (user_id = current_setting('app.user_id')::uuid)`), the database filters every query. Table owners and superusers bypass RLS unless `FORCE ROW LEVEL SECURITY` is set, so the app must connect as a non-owner role — [T: PostgreSQL docs, Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). I did not re-verify this in this session.

**Incidents (consumer and AI-wearable)**
- **Omi (BasedHardware), April 2026, researcher self-disclosure [P, self-published, not independently corroborated].** 17 findings, 14 filed privately on 2026-04-15 (GHSA-4j2c-fmg6-8h42), described as CVSS 10.0. Critical: RCE via `eval()` on Redis data; auth bypass via `ADMIN_KEY` prefix match; a production `ENCRYPTION_SECRET` committed to the public repo, leaving default deployments with "effectively no encryption"; auth bypass via `LOCAL_DEVELOPMENT` returning UID `'123'`. High: SSRF in webhook URLs; path traversal in sync upload; OAuth CSRF (state not validated); **unauthenticated access to shared conversations including speaker names and people profiles** (OMI-08, still unconfirmed fixed as of Aug 10, 2026); a hardcoded admin-panel bypass token. Medium and low: no rate limit on the WebSocket transcription endpoint, container runs as root, unsalted SHA-256 for API keys and BYOK fingerprints. Vendor response: no maintainer comments, no CVE, founder tweeted "team is small, we need maintainers," and the hardening PR was closed without merging. The main fix commit landed on 2026-07-27, 103 days after the report, from an outside contributor. No evidence of actual data access was reported — [P: kasparovabi disclosure](https://kasparovabi.github.io/security-research/2026-04-omi-disclosure.html)
- **Rabbit r1, June 2024.** On June 25, 2024, the Rabbitude group disclosed that since May 16 it had access to Rabbit's codebase containing hardcoded API keys for ElevenLabs, Azure, Yelp and Google Maps. The ElevenLabs key allegedly allowed reading every r1 response ever given (text-to-speech history) and replacing voices. Rabbit rotated the keys, causing brief downtime, and said it had not confirmed compromise of customer data. Rabbitude disputed that and said a fifth (SendGrid) key remained. Rabbit's disclosure came a month after the first contact — [S: Android Authority](https://www.androidauthority.com/rabbit-r1-security-flaw-3455555/); [S: Arnica](https://www.arnica.io/blog/rabbit-r1-data-breach-once-again-shows-the-dire-need-for-improved-secrets-security); [S: Barracuda](https://blog.barracuda.com/2024/07/03/api-keys--api-keys--wherefore-art-thou-always-leaking-); [S: Gigazine](https://gigazine.net/gsc_news/en/20240627-rabbit-r1-jailbreake)
  - Lesson: provider keys (STT/TTS/LLM) held server-side give whole-service access across all users. Third-party processor logs, such as ElevenLabs history, are part of the data at rest.
- **Tea app, July 2025.** (1) On July 25, a Firebase Storage bucket with no security rules (reportedly listable) exposed ~72,000 images: ~13,000 selfies and ID photos from verification, plus ~59,000 from posts and messages. It was "legacy" data from users who signed up before February 2024, which had been kept despite policy. (2) On July 28, researcher Kasra Rahjerdi found ~1.1 million DMs from 2023 to July 2025 reachable through the API with an ordinary user's API key. That is a classic BOLA — [S: Security.org](https://www.security.org/identity-theft/breach/tea-app/); [S: Fox News](https://www.foxnews.com/tech/tea-app-hacked-womens-photos-ids-even-dms-leaked-online); [S: Teiss](https://www.teiss.co.uk/news/tea-app-suffers-second-breach-exposing-11-million-private-messages-after-initial-leak-of-id-photos-16147); [S: Security Affairs](https://securityaffairs.com/180539/data-breach/hackers-leak-images-and-comments-from-women-dating-safety-app-tea.html); [S: Akash Menon, "Not a Hack – Just Bad Defaults"](https://akashmenon.substack.com/p/not-a-hack-just-bad-defaults). No official technical postmortem exists, and reports conflict on whether contact details leaked.
  - Lessons: retention failure (data kept after it was supposed to be deleted) multiplied the blast radius, and backend-as-a-service defaults (Firebase rules) are the isolation layer.
- **Humane AI Pin.** I found no documented cross-user data exposure. One researcher post exploits an unpatched Android CVE (CVE-2024-31317) on the Pin's outdated OS (security patch level 2023-04-01) — [P: researcher post](https://writings.agg.im/posts/hacking_ai_pin/). Its data lived in the Humane.center cloud — [S: TechCrunch 2023](https://techcrunch.com/2023/11/09/humanes-ai-pin/amp). The 2025 HP acquisition and shutdown, with cloud data deleted, is from prior knowledge and was not re-verified here.
- **Bee / Plaud / Limitless.** I found no published cross-user breach for any of them in this session's searches.

### Inferences
- Minimum isolation stack for Owl: (a) every route derives `user_id` from the token, never from the path or body; (b) Postgres RLS with `FORCE`, the app connecting as a non-owner role, and `app.user_id` set per transaction; (c) unguessable object IDs; (d) per-user DEKs, so a query that slips past RLS returns ciphertext encrypted under another user's key that the request context can't unwrap (KMS encryption context = user_id); (e) automated cross-tenant tests in CI, where user A's token fetching user B's object IDs must fail; (f) secrets in a secret manager with scanning (the Omi and Rabbit failures).
- Third-party OAuth tokens add a second axis: a token must be bound to (user, client, scopes), and RLS policies or an API gateway must check scope per data type, not just user (BFLA risk).
- "Share link" features are a known leak path (Omi OMI-08). If added, they need expiry, revocation and scope limits.
- An open-source backend (like Omi) makes committed secrets and dev bypass paths public immediately. Owl's repo is a monorepo, so extra care is needed if it is published.

### Gaps
- I could not verify the Omi findings in GitHub's advisory database. The source is the researcher's own write-up.
- I did not find 404 Media or TechCrunch primary coverage of any lifelog-wearable cross-user leak in 2025–2026 besides the above.
- I did not search Supabase RLS-disabled incidents (e.g. AI-app-builder-generated apps in 2025), which would be a relevant BaaS analog.

## 3. Operator/insider access controls, legal requests (Korea), retention and backups

### Takeaway
In Korea, an operator holding plaintext lifelog data will receive warrants at scale. Kakao, for example, supplied 5.7M+ items under warrants in H1 2024. The only strong defenses against compelled access are not holding the data or holding only ciphertext. Procedural controls (just-in-time access, user-visible access logs, transparency reports, user notification) are expected but don't prevent access. Korean law has required investigators to notify users of 통신이용자정보 (formerly 통신자료) disclosures within 30 days since January 2024, but the operator itself is not barred from disclosing.

### Cited Findings
- Kakao, H1 2024: 19,418 search-warrant (압수수색 영장) request documents, 15,893 processed, 5,715,759 items supplied. Also 2,490 통신사실확인자료 cases and 34 통신제한조치 (interception) cases — [S: SBS Biz](https://biz.sbs.co.kr/amp/article/20000193881)
- Kakao history: in 2014 Daum Kakao announced it would refuse interception warrants and publish transparency reports, then reportedly reversed within a year. It later admitted it did receive 통신제한조치 requests, correcting an earlier denial — [P: Kakao corp press](https://www.kakaocorp.com/page/detail/7790); [P: Kakao privacy-mode notice](https://www.kakaocorp.com/page/detail/7616); [S: Weekly Khan 2015](https://weekly.khan.co.kr/article/201510201003011). Warrant requests to Kakao grew from 3,145 (2015) to 15,153 (2018) — [S: Newspim](https://newspim.com/news/view/20191008000576)
  - Kakao's response was technical, not just policy: "비밀채팅" (E2EE secret chat) and shortened server retention. It showed that warrant exposure is driven by what the server stores — [P: Kakao notice](https://www.kakaocorp.com/page/detail/7616)
- 통신자료 / 통신이용자정보 (전기통신사업법 §83): in 2022 the Constitutional Court ruled §83③ incompatible with the constitution because the subscriber received no notice. An amendment in force since January 2024 (§83의2) requires the receiving prosecutor or investigative agency to notify the user within 30 days, with deferral possible (reported up to 6 months). Bills from August 2024 would require court permission and shorten deferral to 3 months. Committee review is on record for 2025-02-25, and I could not determine the final outcome — [S: Weekly Khan 2024](https://weekly.khan.co.kr/article/202408190600021); [S: 참여연대 공익법센터](https://peoplepower21.org/publiclaw/1954221); [P: 국회 입법예고](https://opinion.lawmaking.go.kr/gcom/nsmLmSts/out/2202675/detailRP)
- MSIT statistics, H1 2024: phone numbers whose 통신이용자정보 were supplied fell 43.7% year-on-year (2,418,668 → 1,361,118) — [S: newsseoul citing 과기정통부](https://newsseoul.co.kr/news/view/1065582612245931)
- Note: 통신자료 (subscriber identity data: name, ID, phone number, etc.) can be requested without a warrant. Content such as transcripts and location history requires a 압수수색 영장, and 통신사실확인자료 (logs, IP, location tower data) requires court permission under 통신비밀보호법. Whether an Owl cloud counts as a 전기통신사업자 (a 부가통신사업자 filing) determines whether §83 applies — [S: Weekly Khan](https://weekly.khan.co.kr/article/202408190600021). The legal classification for Owl is my inference, not sourced.
- Retention failure as breach multiplier: Tea's exposed images were legacy data kept from before February 2024 — [S: Security.org](https://www.security.org/identity-theft/breach/tea-app/)
- Shutdown and acquisition: Limitless gave ~14 days to export before permanent deletion, and critics said 90–180 days is a good sunset practice — [S: Pascal's Chatbot](https://p4sc4l.beehiiv.com/p/limitless-ai-a-case-study-in-how-small-hardware-enabled-ai-companies-transition-their-products-user)
- Apple PCC's "no privileged runtime access" requirement is the strongest stated insider control: no debug or remote shell interfaces in production, so even SREs can't inspect user data — [P: Apple Security Research](https://security.apple.com/blog/expanding-pcc)

### Inferences
- Operator controls to plan for, if Owl holds decryptable data:
  - No standing production data access. Break-glass or just-in-time access needs a ticket, a second approver and a time limit.
  - KMS decrypt calls carry `user_id` encryption context, and CloudTrail-style logs are mirrored into a per-user "who accessed my data" view covering operator, third-party apps and legal requests.
  - Publish a semiannual transparency report: counts of 통신자료 requests, 압수수색 영장 and 통신사실확인자료, and how many were satisfied.
  - Policy: notify the user unless gagged; challenge overbroad requests; supply only the specified date range and data type.
- Backups: encrypt backups under per-user DEKs, or keep backup retention short (e.g. ≤35 days) and document "deleted data disappears from backups within N days." Otherwise crypto-shred claims are false.
- The cheapest legal-request defense is architectural: if the cloud stores only ciphertext with phone-held keys (option 3 or 4 in §1), Owl can answer warrants only with ciphertext and metadata. Metadata such as timestamps, sizes and IPs is still disclosable, so minimize it too.

### Gaps
- I did not verify Kakao's own transparency report numbers from privacy.kakao.com. The figures come from SBS. Naver's numbers were not split out.
- I did not confirm the current text of 전기통신사업법 §83 and §83의2 (whether the court-permission amendment passed) on law.go.kr.
- I did not research 개인정보보호법 obligations specific to location data (위치정보법 사업자 신고/허가 for GPS history). This is likely required if Owl stores location server-side and should be checked.

## 4. Minimizing what is stored (precedents)

### Takeaway
Every major competitor now markets minimization: Bee doesn't store audio, Plaud keeps nothing in the cloud unless sync is on, and Limitless had user-set retention. Storing transcripts only, coarsening location, scoping sync per data type, and setting short retention cuts both breach and warrant exposure, and it is the precedent users expect.

### Cited Findings
- Bee: audio "processed entirely in memory and immediately deleted." Only transcripts and insights are kept, encrypted with device-held keys — [P: Bee blog](https://bee.computer/blog/private-ai). One outlet reports encrypted transcripts are kept 14 days for free users. That is unverified, and Bee's page states no retention period — [S: Pebblous](https://blog.pebblous.ai/blog/amazon-bee-audio-deleted-transcript-kept/en/). Amazon has not documented what happens to a capture that is in progress during a phone call — [S: 9to5Amazon](https://9to5amazon.com/amazon-bee-privacy-explained/)
- Plaud: nothing is persisted in the cloud unless Cloud Sync is enabled. Without sync, AI processing is transient with no persistent copy. Storage is regional (AWS), and no training happens without opt-in — [P: Plaud Trust Center (AU)](https://au.plaud.ai/pages/trust-center); [P: Plaud support](https://support.plaud.ai/hc/en-us/articles/57744166222489-Plaud-s-security-and-compliance)
- Limitless (pre-acquisition): retention configurable from 1 day to forever — [S: UMEVO comparison (competitor blog)](https://www.umevo.ai/blogs/ume-all-posts/limitless-pendant-vs-bee-ai-which-always-on-wearable-recorder-is-best)
- Apple's choice to keep Calendar, Contacts and Mail non-E2EE for interoperability shows that per-category protection levels are an accepted product pattern — [P: Apple 102651](https://support.apple.com/102651)

### Inferences
- Recommended Owl defaults if a cloud is built:
  - Audio never syncs: it stays on the phone, or is offered only as an explicit per-clip upload.
  - Transcripts sync per day or per bookmark, with user-selectable scope.
  - GPS syncs coarsened by default (geohash or ~1 km cell, or "place name" labels only). Precise traces stay on the phone.
  - Sync scope is per data type and matches the OAuth scopes (e.g. `transcripts.read`, `bookmarks.read`, `location.coarse.read`), so the storage design and the grant design share one taxonomy.
  - Server retention defaults to a rolling window (e.g. 30–90 days), with "forever" as an explicit opt-in. Data at rest becomes a cache, not an archive.
- Third-party apps and MCP clients mostly need recent summaries, bookmarks and search results, not full raw history. Serving derived and redacted views (summaries, speaker-anonymized excerpts) lowers what a grant leaks.
- Bystander voices are in transcripts. Minimization such as speaker redaction and dropping non-user speech helps with 개인정보보호법 exposure for people who never consented. This needs legal checking.

### Gaps
- I found no competitor that coarsens location server-side by default. I didn't find a primary source on Limitless or Omi location handling.
- Omi's data-minimization settings were not reviewed beyond the disclosure.

## 5. Certifications and practices expected (brief)

### Takeaway
Competitors in this space advertise SOC 2 Type II plus ISO 27001/27701 (Plaud), or third-party security reviews (Bee via Trail of Bits). In Korea, ISMS or ISMS-P becomes legally mandatory once information-and-communications service revenue reaches ₩10B, or daily average users reach 1M (prior-year basis). Below that it is voluntary, but it signals trust.

### Cited Findings
- Plaud Trust Center: SOC 2 Type II (security, availability, confidentiality), ISO/IEC 27001 and 27701 (ISO 27001 attributed to Sensiba), and HIPAA claims. HIPAA applies only with a signed BAA for organizations — [P: Plaud trust](https://www.plaud.ai/pages/trust); [P: Plaud Drata page](https://www.plaud.ai/pages/drata); [S: Layer3Labs](https://www.layer3labs.io/guides/is-plaud-hipaa-compliant)
- Bee: Trail of Bits security review plus a technical white paper (2026-09) — [P: Bee blog](https://bee.computer/blog/private-ai)
- ISMS mandatory targets (정보통신망법 §47의2, 시행령 §49) include providers with prior-year 정보통신서비스 revenue ≥ ₩10B, or a daily average of ≥ 1M users over the last 3 months of the prior year, among other categories (e.g. ISPs, IDCs, total revenue ≥ ₩150B for certain entities). Holding ISMS-P satisfies the ISMS obligation. The fine for a mandatory entity that isn't certified is up to ₩30M (§76) — [P: KISA ISMS-P](https://www.kisa.or.kr/1050602); [S: itwiki ISMS-P 인증 대상](https://www.itwiki.kr/w/ISMS-P_%EC%9D%B8%EC%A6%9D_%EB%8C%80%EC%83%81); [S: Alchera blog](https://www.alchera.ai/resource/blog/ISMS-certification-mandatory-subject)
- Criticism: ISMS-P is often questioned after breaches (certified firms still get hacked) — [S: Byline Network, Nov 2025](https://byline.network/2025/11/20-518/)

### Inferences
- For a small Korean startup's Owl cloud: ISMS is not mandatory at launch. Practical priorities are a third-party penetration test or code review before launch (Bee and Trail of Bits are the precedent; Omi shows the cost of skipping it), a published security and transparency page, a bug bounty or `security.txt` with an SLA (Omi's 103-day fix is the anti-pattern), then ISMS-P or SOC 2 when B2B or partner deals require it.
- ISMS-P (with the "P" privacy component) is the natural target for an app holding voice transcripts and location of Korean users, more relevant locally than SOC 2.

### Gaps
- I did not verify the exact 시행령 §49 wording on law.go.kr. Thresholds are from KISA and secondary sources.
- I did not check whether Omi or Limitless published SOC 2 or ISO certificates.
